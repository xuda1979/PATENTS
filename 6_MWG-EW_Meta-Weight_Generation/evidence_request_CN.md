# 研发取证需求单
# MWG-EW 专利申请支撑证据

---

## 一、目的

本文件用于向研发、系统、内核和训练团队明确说明：为了增强 `MWG-EW` 专利申请的授权质量和后续答审韧性，需要补充哪些技术证据、这些证据分别支撑什么法律和技术主张、以及优先级如何排序。

本文件面向的对象包括：

1. 内核开发工程师；
2. 推理系统工程师；
3. 训练/蒸馏工程师；
4. 性能分析工程师；
5. 项目负责人或技术经理。

---

## 二、证据目标

本案最关键的可验证技术主张不是“能生成权重”本身，而是以下组合：

1. 运行时根据激活特征和层标识生成临时权重描述子块；
2. 临时权重描述子块仅驻留于片上存储器；
3. 使用后释放、覆写或清零；
4. 在全生命周期内不回写外部存储器；
5. 解码场景中节省的外部存储可重分配给 KV Cache；
6. 训练场景中目标层局部梯度块不进入优化器状态缓存且不参与跨节点同步；
7. 外部存储流量下降，矩阵计算单元利用率改善。

因此，研发侧的证据应当优先围绕“内存路径”“执行生命周期”和“训练同步路径”采集，而不是只给训练 loss 或参数量。

---

## 三、证据优先级

### P0：最关键证据

这些证据对授权和答审帮助最大，建议优先完成。

1. **不回写证据**
   - 目标：证明生成的临时权重描述子块及其对应临时目标权重分块未写回 HBM/DRAM/host memory。
   - 形式：Nsight Systems / Nsight Compute 截图、事件计数、内存访问日志、内核 trace。
   - 作用：直接支撑“片上驻留 + 不回写外部存储器”。

2. **外部存储流量对比**
   - 目标：对比稠密基线与 MWG-EW 在目标 FFN 块上的 HBM bytes read / write。
   - 形式：表格 + profiler 输出。
   - 作用：支撑技术效果“降低外部存储流量”。

3. **参考实现一致性**
   - 目标：证明融合路径与参考 PyTorch 路径数值一致。
   - 形式：误差表、最大绝对误差、相对误差、随机种子下重复性结果。
   - 作用：证明发明具有可实施性，而非停留在概念层面。

4. **训练同步截断证据**
   - 目标：证明目标层局部梯度块未进入优化器状态缓存，且未参与 All-Reduce 或等效同步。
   - 形式：通信统计、抓包结果、优化器状态占用统计、训练 trace。
   - 作用：直接支撑训练与通信防御层。

### P1：高价值证据

1. **吞吐/时延对比**
   - 目标：证明在带宽受限硬件上吞吐或时延改善。
   - 形式：tokens/s、token latency、batch latency、rank sweep 图。
   - 作用：支撑“将部分路径由带宽受限转向计算受限”。

2. **片上存储占用与 tensor core 利用率**
   - 目标：说明所述方案确实把负担转到片上执行和矩阵计算单元。
   - 形式：shared memory 使用、register pressure、tensor core occupancy、stall reason 对比。
   - 作用：强化硬件执行技术效果。

3. **解码 KV Cache 受益**
   - 目标：证明节省的外部存储空间被转化为更大的 KV Cache 或更长上下文能力。
   - 形式：最大上下文长度对比、KV Cache 容量对比、双缓冲 on/off 对比。
   - 作用：支撑推理解码防御层。

4. **训练/蒸馏恢复效果**
   - 目标：证明从预训练稠密模型迁移后质量可恢复。
   - 形式：loss 曲线、perplexity、teacher-student KL、下游任务结果。
   - 作用：支撑迁移路径和实用性。

### P2：增强型证据

1. **rank sweep**
2. **部分层替换 vs 全层替换**
3. **直接低秩因子 vs 基库重构**
4. **token 分组复用 on/off**
5. **单内核 vs 分裂 kernel**
6. **optimizer / communication gate on/off**

这些证据对主权项不是必须，但对后续分案和从属权利要求很有帮助。

## 四、具体取证项目

### 1. 内存路径证据

研发团队应提供：

1. 稠密基线的 HBM bytes read / write；
2. MWG-EW 路径的 HBM bytes read / write；
3. 每个生成块的 HBM write 是否为零或近似为零；
4. 是否存在将等价完整稠密矩阵写入外部存储器的事件；
5. 若存在调试写回，需要注明调试模式与正式推理模式区别。

建议输出格式：

- 一页截图；
- 一页表格；
- 一页简述。

### 2. 生命周期证据

研发团队应提供：

1. 当前块生成时间点；
2. 当前块消费时间点；
3. 当前块释放/覆写/清零时间点；
4. 下一块生成时间点；
5. 是否满足“当前块释放后再生成下一块”。

建议输出格式：

- 时序图；
- 内核伪代码；
- 事件 trace。

### 3. 数值正确性证据

研发团队应提供：

1. 参考 PyTorch 路径输出；
2. 融合内核 路径输出；
3. 最大绝对误差；
4. 平均相对误差；
5. 多次运行一致性。

### 4. 解码与 KV Cache 证据

研发团队应提供：

1. 固定外部存储预算下 dense baseline 最大上下文长度；
2. 固定外部存储预算下 MWG-EW 最大上下文长度；
3. KV Cache 可用容量变化；
4. 双缓冲 on/off 的时延对比。

### 5. 训练同步与优化器证据

训练团队应提供：

1. dense baseline All-Reduce bytes；
2. MWG-EW All-Reduce bytes；
3. 目标层局部梯度块是否出现在同步 trace 中；
4. dense baseline optimizer state memory；
5. MWG-EW optimizer state memory。

### 6. 质量恢复证据

训练团队应提供：

1. 稠密模型 baseline loss / ppl；
2. 替换后未经训练模型的 loss / ppl；
3. 继续训练或蒸馏后的恢复结果；
4. 恢复曲线；
5. 隐状态匹配或 logit 匹配指标。

### 7. 性能收益证据

系统团队应提供：

1. 稠密基线 tokens/s；
2. MWG-EW tokens/s；
3. 稠密基线 token latency；
4. MWG-EW token latency；
5. 不同 rank 下的吞吐/时延结果；
6. 不同 batch size 下的趋势。

## 九、结论

对本案最有价值的证据，不是单纯证明模型“能跑”，而是证明：

1. 临时权重描述子块确实是运行时生成；
2. 这些块确实只在片上存储器中短暂存在；
3. 它们确实没有回写外部存储器；
4. 解码场景中节省的外部存储是否转化为 KV Cache 或上下文收益；
5. 训练场景中目标层局部梯度块是否没有进入优化器状态和同步路径；
6. 这样做是否确实降低了外部存储流量、同步流量并改善了执行效率。

只要研发侧围绕这四点交付证据，本案的申请质量和后续答审能力都会显著提升。
